# 模型选择下拉固定头部设计

日期：2026-03-29

## 背景

当前 `seedclaw` 的模型选择下拉已经抽成共享组件：

- `src/components/models/ModelSelectMenuContent.vue`

该组件已被以下入口复用：

- 聊天输入框中的模型下拉
- 智能体概览页中的默认模型下拉

当前菜单内容整体作为一个滚动区域，导致以下问题：

- “选择模型”标题会随着列表一起滚动
- 搜索栏会随着列表一起滚动
- 当模型数量较多时，用户滚动列表后会失去搜索入口，需要重新滚回顶部

本次目标是在不改变现有业务行为的前提下，让“选择模型”标题与搜索栏始终固定在菜单顶部，只有模型列表区域滚动。

## 目标

- 让“选择模型”标题固定在模型菜单顶部
- 让搜索栏固定在模型菜单顶部
- 让模型项列表成为独立滚动区域
- 保持聊天页与智能体概览页两处行为一致
- 保持现有搜索逻辑、选中高亮、分组展示、unknown current 行为不变
- 保持现有外层弹层定位与开关逻辑不变

## 非目标

- 不调整聊天页模型下拉的触发按钮与开关逻辑
- 不调整智能体概览页模型下拉的浮层定位逻辑
- 不修改模型搜索匹配规则
- 不修改模型选择后的业务回调协议
- 不改 i18n key 与现有文案来源
- 不重做 provider 分组标题样式，只做必要的 sticky 偏移修正

## 需求结论

用户确认后的目标行为如下：

1. “选择模型”四个字始终吸顶
2. 搜索栏始终吸顶
3. 其他内容保持原样
4. provider 分组标题依然保留原有 sticky 分组提示效果
5. unknown current 项、选中态高亮、勾选图标、过滤逻辑保持不变

## 方案对比

### 方案 A：直接给标题与搜索区加 sticky

在当前组件结构上直接把标题和搜索区标记为 `sticky top-0`。

**优点**
- 改动小
- 不需要新增额外滚动层

**缺点**
- 头部与列表仍处在同一滚动容器内，层级关系更脆弱
- provider 分组标题本身也有 sticky，容易和头部发生覆盖冲突
- 对后续样式维护不够清晰

### 方案 B：拆分为固定头部 + 独立滚动列表

将组件内部改成两段结构：

- 顶部固定头部：标题 + 搜索栏
- 底部滚动列表：unknown current + provider 分组 + 模型项

**优点**
- 结构语义清晰
- 吸顶行为稳定
- 更容易处理 provider 分组标题的 sticky 偏移
- 两个入口复用时效果一致

**缺点**
- 需要调整组件内部容器层级
- 需要为列表滚动区重新分配高度

### 方案 C：在各父组件外层分别实现固定头部

在 `ChatInput.vue` 与 `AgentOverview.vue` 各自处理固定标题与搜索栏，不改共享组件。

**优点**
- 可为不同页面定制视觉细节

**缺点**
- 重复实现
- 容易造成两处行为漂移
- 与共享组件设计方向相违背

## 推荐方案

采用 **方案 B：固定头部 + 独立滚动列表**。

理由：

- 本次需求本质上是组件内部布局与滚动责任的重新划分，而不是单纯补一条样式
- 共享组件是两个入口的公共实现，直接在共享组件中完成结构调整最一致
- 通过“头部固定、列表滚动”的明确分层，最容易保证移动端与桌面端都稳定工作

## 组件设计

### 受影响文件

- `src/components/models/ModelSelectMenuContent.vue`
- `tests/model-select-menu-content.test.ts`

父组件：

- `src/components/chat/ChatInput.vue`
- `src/components/agents/tabs/AgentOverview.vue`

本次仅依赖父组件继续提供现有外层弹层容器，不修改其状态与定位逻辑。

### 新结构

`ModelSelectMenuContent.vue` 内部改成以下结构：

1. 根容器：纵向布局
2. 固定头部区
   - 标题
   - 搜索栏
3. 列表滚动区
   - unknown current 项
   - provider 分组标题
   - 模型按钮项

这样外层浮层仍然负责：

- 最大高度限制
- 面板宽度
- 固定/绝对定位
- 打开与关闭

组件内部只负责“头部固定 + 列表滚动”。

## 视觉与滚动行为

### 固定头部

固定头部需要满足：

- 顶部标题与搜索栏始终可见
- 使用 `bg-base-100` 保证滚动内容不会透出
- 使用更高层级，确保位于滚动列表与 provider sticky 标题之上
- 保持当前标题、搜索框的视觉风格，不做不必要改动

### 列表滚动区

列表滚动区承担所有纵向滚动：

- unknown current 项随列表一起滚动
- provider 分组标题继续 sticky
- 模型项继续按当前样式渲染

### provider 分组标题

当前 provider 标题已使用 sticky 行为。本次需保留该能力，但它的 `top` 偏移不能再是相对整个菜单的 `0`，而应避开固定头部高度。

否则会出现以下问题：

- 分组标题顶到标题/搜索栏下面时发生重叠
- 分组标题遮住搜索框底部
- 滚动时层级错乱

因此需要将 provider 标题的 sticky 偏移值调整为“固定头部总高度”对应的值。

## 交互行为

以下交互全部保持不变：

- 搜索输入通过 `searchText` 驱动过滤
- 搜索范围仍为 `m.name` 与 `m.id`
- 搜索结果仍按 provider 分组展示
- 点击模型项继续 emit 完整 `provider/modelId`
- 当前模型高亮逻辑保持不变
- unknown current 的展示逻辑保持不变
- 聊天页选择后仍调用现有 `handleModelSelect`
- 智能体概览页选择后仍通过现有回调关闭菜单并更新模型

## 实现边界

### 允许修改

- `ModelSelectMenuContent.vue` 的布局结构
- 固定头部与滚动区的 class 组织
- provider sticky 标题的偏移值
- 针对新结构补充测试

### 不修改

- `ChatInput.vue` 中模型菜单的显示/关闭状态管理

- `availableModels` 数据结构
- `currentModel` 的格式
- `select` 事件协议
- 搜索算法

## 风险与规避

### 风险 1：provider sticky 标题与头部重叠

**原因**：分组标题原先相对整个滚动容器吸顶，结构改变后需要让位给固定头部。

**规避**：显式调整 provider sticky 的 `top` 偏移，使其位于搜索栏下方。

### 风险 2：列表区没有正确继承高度，导致无法滚动

**原因**：如果内部结构改为 flex 后未正确设置 `min-h-0` / `overflow-y-auto`，子区域可能不会成为可滚动容器。

**规避**：根容器和列表区都明确设置适合 flex 滚动布局的 class。

### 风险 3：聊天页和智能体页视觉表现不一致

**原因**：两处父容器尺寸与定位不同。

**规避**：仅在共享内容组件内部实现固定头部，父容器保持原样，减少差异来源。

## 成功标准

完成后应满足：

- 聊天页模型下拉中，“选择模型”与搜索栏始终固定在顶部
- 智能体概览页模型下拉中，“选择模型”与搜索栏始终固定在顶部
- 滚动时只有模型列表区域移动
- provider 分组标题仍能正常提供滚动中的分组提示
- 现有搜索、选中态、unknown current 行为不回退
- 两个入口继续共用同一个 `ModelSelectMenuContent.vue` 组件
